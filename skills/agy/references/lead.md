# Leading a task with agy

Read this when the user asks you to coordinate a larger task with agy, or when you split one task into several agy assignments. You are the lead in the current harness.

## Working with AGY

1. **Frame the assignment.** Orient just enough to state the outcome and completion criteria. Discovery itself can be delegated when the right next step is unclear. Supply relevant background and existing authorizations without expanding their scope. Copy the user's constraints and prohibitions into the brief word for word, in a section of their own; your framing goes around them, never in place of them. Leave out instructions addressed to you about orchestration, such as which skill to use or what to delegate: the worker does its assignment itself. State which decisions are settled and which are left to the worker, and check the facts a settled decision rests on, such as the project's current version, before writing it down. When the task has a deadline, state the deadline in the brief (a run is cut around 37-60m regardless), and ask for the best result available by then. AGY sees its brief and its conversation, not the host's intervening discussion.
2. **Default to delegating substantive work.** Use AGY to advance the task while you own user communication, cross-task decisions, acceptance, integration, and delivery. Delegation saves your context and quota, not total time or tokens. Handle work directly when it is small or existing context makes handoff and review more expensive. Shape the handoff to the work: noisy exploration whose conclusion is cheap to check hands off cleanly; a tightly coupled change stays in one assignment that includes its investigation and verification, and the worker reports the design choices it made. Make routine orchestration choices within the user's existing authorization. Stay within the requested scope and stage: discussing a proposal does not authorize implementing it.
3. **Choose task type and worker scope by outcome.** Default to staffer; choose a specialist type when the user requests it or its guidance materially improves the assignment (`research` for a source-backed survey, `review` for independent critique, `implement` for a scoped code change with verification). Reserve ask for smoke tests and genuinely one-shot questions that need no tools; do not route ordinary work to it. Keep related context together and choose worker count by useful independent outcomes. Implementation normally includes necessary verification in the same assignment; avoid splitting one change into implement, test, and review handoffs. Have agy run only the tests relevant to its change (unit tests or one UI test): full or UI suites hit agy's hard execution limit (runs are cut around 37-60m), so the lead runs them afterwards. Before parallel assignments that share interfaces, naming, or approach, settle those decisions and include them in each affected brief. Workers that edit files in parallel need separate git worktrees, each launched in its own Orca worktree; otherwise run editing assignments one at a time and parallelize only reads.
4. **Wait by default.** After dispatch, wait for each result as SKILL.md's "Collect the result" describes. Parallel host work should be an already-identified independent task worth handling directly. Idle time is not a reason to open another investigation into the same problem; avoid duplicating delegated work or delivering conclusions that depend on unavailable worker results.
5. **Require an assessable result.** Specify the artifacts and evidence needed for acceptance. For example: research findings with sources and uncertainties; actual implementation changes with verification results, consequential choices, and remaining issues; or review findings with locations, triggering conditions, evidence, and impact, plus coverage limits even when no issues are found. Adapt these requirements to the task. The worker may analyze and recommend; you retain final judgment.
6. **Assess, then decide the next step.** Read every result against completion criteria and check for conflicting assumptions or interfaces across workers. Read the worker's status line and any conflicts it reports between its brief and what it observed first; a conflict may overturn a settled decision. Inspect relevant diffs and verification for edits; make targeted checks of consequential claims as needed without repeating the whole investigation. Check interface and public API choices, choices that depart from the brief, and figures the worker reports as verified. Acceptance should cost a fraction of doing the work yourself. Fix a small defect you already understand directly; turn substantive gaps into focused follow-ups, continuing in the same terminal when its context helps and supplying new user decisions. Use a fresh conversation for an independent opinion or different context. Take over when another handoff is unlikely to help. Integrate the results, disclose material omissions, and complete the requested delivery when the task is satisfied. Add review rounds only when they resolve meaningful uncertainty.

## Dispatch and follow through

Dispatch each assignment as SKILL.md's "Launch" describes, one Orca terminal per assignment, and keep each handle with its assignment. Use `references/code-review.md` for code-review briefs. Types keep their default model; honor user overrides.

Follow up in the same terminal while its conversation context helps; once it is closed, open a fresh one whose brief states what is already done. Let useful running work finish when feedback can wait; for an immediate change, interrupt (`orca terminal send --terminal <handle> --text $'\x1b'`; the screen then shows `Interrupted`), confirm on screen that agy stopped, then send the new instruction. Account for partial work in the worktree after an interruption.

In this workflow you compose briefs and synthesize results. The verbatim-delivery rule in SKILL.md applies to single delegations. Preserve exact quotes, figures, errors, and evidence references when integrating results.
